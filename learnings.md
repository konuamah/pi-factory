# learnings.md

- When repository topology is ambiguous, use deterministic discovery to gather candidate roots/scripts, then use a reasoning step to choose execution strategy.
- Verification failures should be separated into harness/config selection issues versus real project code issues.
- Do not treat transient worktree content as authoritative long-term project guidance.
- Persist verification reasoning artifacts so cwd, command selection, and failure classification can be inspected later in logs/show output.
- Resume policy should react to failure classification: re-plan verification for harness/config or repo-script issues, and resume repair/verification for real code failures.
- Builder sessions run in per-task sibling worktrees, but the compiled prompt never named the workspace path. Models (MiniMax-M2.7) resolved relative repo hints like `backend/src/...` against the main checkout, so edits landed in the main repo while the worktree diff stayed clean, producing `implementation-failed` (task produced no changes). Always inject the task workspace path into the builder prompt so tool calls target the worktree, and re-emphasize on no-change retry.
- Fast worktrees should share immutable package-manager/compiler caches while keeping source, git index, dependency manifests, `node_modules`, virtualenvs, and other writable workspace state isolated. Make this language-neutral and drive setup through the repo's configured setup command rather than a framework-specific installer.
- Doctor readiness should validate both model routing resolution and Pi-visible provider/model availability, not just the presence of config keys.
- Broad Factory Concierge setup should produce model-ready config by assigning Pi-visible models to all Factory roles, not only direct users to model inspection.
- Stage handoffs should preserve both human-readable summaries and structured artifacts. If a controller-native phase, planner decision, interview answer, or baseline-unrelated verification result affects later behavior, downstream stages and approval UI need the structured fact, not only a text blob.
- Stage-name dependencies (e.g. `dependsOn: [plan]`) must resolve to task ids when passing dependency context to the builder; comparing stage names to task ids silently empties dependency context.
- Controller-native stages (plan, discover, interview) should appear in task artifacts as `done` with `controllerHandled` and artifact path refs, so run inspection matches the runtime story.
- Interview answers are authoritative human facts: persist them as a structured `interview-decisions.json` and thread them into planner, builder context, reviewer, and approval — a text blob alone is brittle.
- Planner intent should be captured as a structured `implementationContract` (target files, implementation steps, verification checks, non-goals, risks, blockers) so downstream stages can inspect it, with best-effort extraction from prose as the backward-compatible baseline; Builder context should receive this handoff before long guidance so it does not reconstruct the plan by broad rediscovery.
- Preserve raw user goals for audit, but strip pasted Pi prompt-template wrappers from model-facing task objectives. Otherwise Planner Mode text such as "Do not write production code" can leak into Builder prompts and override the role Factory is trying to run.
- Baseline-unrelated failures: warn and proceed, but make the debt explicit at final approval. The task-specific contract can pass while repository debt remains; the UI must say so rather than pretending full-green.
- Discovery should report implementation-surface status as structured JSON, including `implementationSurface: "missing"` for empty or greenfield repos. Do not rely on plain-text sentinel failures when the planner can use the structured status to choose new files.
- Verification planning should allow an empty command selection only when no configured or discovered runnable commands exist, then record incomplete verification with a missing automated-checks result instead of crashing before `verification.json` is written.
- Landing should evaluate dirty target state by file overlap, not mere presence. Unrelated Pi/Factory runtime files are evidence, not blockers, when the current checkout is already the target branch and feature files do not overlap.
- Keep new Factory runtime features split into focused coordinator, AI, Git, and type modules so files stay near 400 lines or under and negative paths remain readable.
- Pi SDK assistant messages can report `stopReason: error` with empty text. Preserve that as executor failure, and pass project-aware SDK services plus an explicit `tools` array so provider/session errors do not collapse into misleading "no output" failures.
- Discovery evidence must observe tracked project config: skip transient Factory subpaths (.factory/runs, dependencies, cache, logs) rather than the whole .factory directory, or confirmed findings about .factory/config.yaml are rejected as hallucinated.
- Landing guards must match the failure they name: pass only the files the guard reasons cite into the diagnoser, and never block required landing on verification "incomplete" (no runnable commands) — the human approval gate already sees that status.
- Once Git landing succeeds, write durable landing artifacts immediately. Post-landing verification is follow-up evidence, not permission to lose or hide an already-landed candidate.
- Harness-enforced limits must not depend on every call site remembering to pass them: the Pi executor now applies Factory default model/total timeouts when limits are missing or partial, because one omitted field silently disabled every watchdog and hung a run forever.
- Never accumulate raw streaming events (message_update/tool_execution_update carry cumulative message snapshots) into result events: it is quadratic and hit V8 max string length in JSON.stringify ("Invalid string length") on a 131MB planner-execution.json. Keep deltas in outputChunks, keep only terminal events.
- Benchmark layer added: readRunArtifacts() is now the single typed reader for run dirs (missing vs corrupt reported separately), and scoreFactoryRun()/summarizeBenchmarkResults() renormalize weights around null pillars instead of scoring unmeasurable things as 0 or 1.
- Interview continuity is unmeasurable when the answer only confirms the question's recommendations (all answer tokens appear in the question): report null, not a pass based on a plan existing.
- Harbor task files must live under environment/ (that directory is the Docker build context) - a custom fixture/ directory is never copied, and tests/ must stay OUTSIDE environment/ or the rubric ships into the agent image.
- Harbor 0.22 parses /logs/verifier/reward.json (verifier/verifier.py); the adapter guide still documents reward.txt. Write both when a task must satisfy both sources.
- Factory's Pi SDK path must create session SERVICES (createAgentSessionServices) so installed provider packages register their models; a bare ModelRuntime.create() only knows built-in providers and cannot resolve commandcode (field-observed: ModelProviderResolutionError on the real trial).
- Headless model routing must inject provider/model into .factory/config.yaml, not only pass modelOverrides: verification reads config.models.planner directly (verification-phase2), so a config without a models block falls back to a provider-less default and dies at verification.
- bombsite-02 status-surface: the interview decides the surface's content and the grader checks those decisions verbatim (id, heading, status text, position), so interview-to-plan-to-build continuity is what's being measured.
- bombsite-03 verification-adaptation: seed a stale configured lint command (tools/lint.mjs that does not exist); the grader keeps the repo green via the real smoke check so the agent must adapt around the broken lint, never invent.
- bombsite-04 baseline-debt: the fixture seeds unrelated broken JS (legacy/old-script.js) and the grader enforces scope preservation (debt file still present AND still broken); the Dockerfile must COPY legacy/ explicitly or the debt silently never ships.
- bombsite-05 repair: seed a verification check that fails until the interview-decided change is made (verify-personalization.mjs); the run must turn it green via repair. Dockerfile copies from the previous template can leave stale COPY lines (legacy/) that break the build.
- Performance buckets must treat events as wall-clock intervals: MODEL = assistant message windows only (tool-result messages inflate it), TOOLS = union of tool intervals (Pi runs tools in parallel; sum double-counts), FACTORY VERIFY is inside agent_execution, AGENT_OTHER is the remainder with an overlap warning.
- Pi SDK tool_execution_start/end are boundary markers, not duration brackets: real tool work happens inside the SDK's agent loop between them, so end-start ≈ 0 (verified on a real trial: 22 events, 0 DSML events). Tool durations need SDK-side timing; counts are meaningful, wall-time lands in AGENT_OTHER.
- Performance summaries must separate "known bottlenecks" (measured buckets) from "unresolved" (unattributedAgentMs): the biggest bucket can be the least explainable. Label TOOLS events vs calls distinctly (22 events = 11 calls) to avoid conflating them in later analysis.
- Prebuilt-image experiment (bombsite-01, gpt-5.4-mini, 3 runs): baking nvm+node+pi into the task Dockerfile + idempotent agent install() dropped median agent_setup 80.9s->16.6s and median TOTAL 353.9s->284.9s (~19% end-to-end). Harbor rebuilds the env per trial but Docker layer-caches the bake, so only the agent's runtime reinstall was the real cost.
- Performance instrumentation must include builder-execution-<taskId>.json: a generic *-execution.json glob silently dropped the builder artifact, inflating UNATTRIBUTED from ~28s to ~123s. executionArtifactsFrom() now assembles all role artifacts (discovery/planner/reviewer/builder/repair/interview).
- LLM judge for benchmark quality: judgeRunQuality() scores all 7 pillars via a strict-JSON prompt over run artifacts; silently returns undefined without an executor (deterministic score stands), never merges into deterministic pillars, and needs the harness's configured executor (bare standalone SDK sessions return empty output without the injected Pi config).
- Headless judge wiring: FACTORY_PI_JUDGE=1 scores the finished run with the LLM judge after completion (same executor+model, writes judge.json next to the run dir); judge failures are swallowed and the deterministic score stands.
- Concierge-launched setup should interview before it writes: route `/factory ask ... setup ...` into a setup-specific user-input pass using the bundled grilling pattern, then treat those answers as authoritative over heuristic or LLM recommendations.
- Factory Concierge runtime knowledge belongs in focused `.pi/skills/factory-*` operational skills. `docs/factory/` is internal engineering reference for Factory source work and debugging, not the normal Concierge prompt layer.
- Factory run naming should preserve the full user prompt as `goal` and add a deterministic short `title` for list/status/dashboard display; never use a model call or overwrite audit intent just to make the UI cleaner.
- Planner task titles are metadata, not audit records: derive them from the deterministic short run title and keep the full pasted prompt only in `goal`, prompts, and artifacts so long-content tasks do not poison status/log surfaces or model-facing task labels.
- A run ending in a broad phase like `implementation-failed` must surface the latest `task.failed` reason in final output and show views; users need the actionable executor error (`model-timeout`, missing skill, no changes), not just the controller phase.
- Watchdog limits now distinguish Activity vs Progress vs Completion. A model streaming text resets `modelIdleTimeoutMs` (activity) but does not prove task progress; only tool start/result and turn transitions count as meaningful progress. Tool execution pauses the idle watchdog and is bounded by `toolTimeoutMs`; the whole turn is bounded by `turnTimeoutMs` (hard); the whole run shares one absolute `runDeadlineAt` set by the controller from `runTimeoutMs` (true run-level budget, not reset per prompt).
- `modelTimeoutMs` and `totalRunTimeoutMs` are deprecated aliases: `modelTimeoutMs` -> `modelIdleTimeoutMs`, and `totalRunTimeoutMs` was misnamed (it was always per-turn) -> `turnTimeoutMs`. Effective config normalizes aliases to canonical names so executor code never reasons about both spellings.
- Every `executor.timeout` event carries detailed diagnostics: timeoutType, reason, limitMs, elapsedMs, turnElapsedMs, runElapsedMs, lastActivityType/At, lastProgressType/At, executionState, activeTools, activityCounts, progressCounts, graceUsed. Use these to distinguish a silent provider from a talkative-but-idle model.
- Bounded adaptive grace is deterministic: at most one `adaptiveGrace.durationMs` extension per turn, granted only when the model actually goes quiet past the idle limit (not up-front on arming), never for tool timeouts, and never past turn/run deadlines.
- Run deadline is threaded into every run-scoped agent executor call: discovery, planner, interview, builder, repair, reviewer, landing, verification planner, file-resolution, planner-validation, and failure classifier all receive `limits` with the shared `runDeadlineAt`. Auxiliary executors (setup, benchmark judge, review provider, constitution scan) are not run-scoped and keep defaults.
- Once a change has landed, post-landing verification runs against the landed target checkout (`mergeCwd`), not the stale pre-landing worktree; and when the only failures were already classified `baseline-unrelated` + `ignore` + non-retryable, do not launch a repair agent — its edits could not change the already-landed commit. Record `repairAttempted: false` and a `landing.post_verification_repair_skipped` event instead. This turned a ~6.5-minute wasted repair session into an immediate, honest finalize.
- Final review should scale with the candidate diff. Build an authoritative review surface from committed changed files, the git diff, direct imports/dependencies, plan contract, and verification result; use deterministic review for trivial low-risk one-file changes, and reduce non-trivial final review to scoped `read` access instead of repo-wide search tools.
- Factory SDK tool activity should be normalized once into concise `tool.started`/`tool.completed` events for live UI, logs, and show views. Keep raw SDK events in execution artifacts for debugging, but make the terminal/widget trail readable enough to answer "what is it reading/writing/running?" without opening JSON.
