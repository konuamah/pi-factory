# Codebase Constitution

## Purpose

Use this skill to inspect an existing codebase and create a factual `CONSTITUTION.md` that describes how the repository is actually built, organized, tested, secured, deployed, and maintained.

The 120 areas below are the scan schema.

The skill is **descriptive first, not prescriptive**:
- Discover what exists.
- Infer conventions only from strong repeated evidence.
- Never invent missing rules.
- Never force an architecture or practice that the repository does not use.
- Mark missing, uncertain, and non-applicable areas explicitly.

## Output

Create or update exactly one persistent repository file:

```text
CONSTITUTION.md
```

Do not create extra audit reports, architecture documents, TODO files, or scanner artifacts unless the user explicitly asks.

Temporary scan scripts may be created outside the repository or in an OS temp directory, but must be read-only toward the repository and removed after use.

---

# Core Operating Rules

1. Inspect before concluding.
2. Prefer repository evidence over assumptions.
3. Prefer deterministic discovery over manual guessing.
4. Separate **explicit rules** from **inferred conventions**.
5. Every meaningful conclusion should point to evidence.
6. Never scan generated/dependency directories unless needed.
7. Do not modify source code while building the constitution.
8. Do not install packages just to perform the scan unless the user explicitly allows it.
9. Do not execute untrusted application code merely to inspect it.
10. Preserve user-authored content in an existing `CONSTITUTION.md` unless it is clearly generated by this skill.
11. If evidence conflicts, record the conflict instead of silently choosing one side.
12. Keep the final constitution compact enough to be useful to humans and coding agents.

---

# Status Model

Use one of these statuses for every area:

- `DEFINED` — explicitly configured, documented, or enforced.
- `INFERRED` — strongly and consistently visible in the repository but not explicitly declared.
- `NOT_DEFINED` — applicable, but no reliable rule or convention was found.
- `NOT_APPLICABLE` — the area does not apply to this repository.
- `UNCERTAIN` — evidence exists but is incomplete, contradictory, generated, or ambiguous.

Use confidence only for inferred or uncertain findings:

- `HIGH`
- `MEDIUM`
- `LOW`

## Agent Interpretation Contract

The generated constitution is not only documentation. It is also repository context for coding agents.

Agents consuming `CONSTITUTION.md` should interpret statuses as follows:

- `DEFINED` — treat as an established repository rule or fact. Follow it unless the user's task explicitly requires changing it.
- `INFERRED` — prefer the convention, but verify nearby/relevant code before making a change that depends on it.
- `NOT_DEFINED` — no repository-wide rule exists. Follow the closest existing code and avoid inventing a new global standard unnecessarily.
- `NOT_APPLICABLE` — ignore for normal implementation decisions.
- `UNCERTAIN` — do not rely on the finding alone. Inspect the relevant files before deciding.

When evidence conflicts, the agent must not treat either side as authoritative without resolving the conflict for the current task.

### Authority Order

When deciding what an agent should follow, use this order:

1. Current user instruction
2. Explicit human-authored repository instructions
3. Enforced configuration or executable build/CI behavior
4. Current source-code behavior and repeated conventions
5. Generated `CONSTITUTION.md` inference
6. Generic best practice

A generated inference must never override explicit repository instructions or actual enforced configuration.

# Scan Workflow

## Phase 1 — Read Repository Instructions

Before scanning broadly, look for and read repository-level instructions such as:

```text
AGENTS.md
CLAUDE.md
README.md
CONTRIBUTING.md
DEVELOPMENT.md
ARCHITECTURE.md
SECURITY.md
docs/
.github/
```

Treat these as explicit evidence, but verify that they still match the repository.

If instructions conflict with source/configuration, record the conflict.

Prefer tools already present on the system:


- monorepo vs single project

- tests
- CI/CD files
- containers

## Phase 3 — Build the Scan Profile

Adapt the scan to the repository.

Examples:

```text
Next.js
→ routes, layouts, server/client components, API handlers,
  middleware, environment handling, tests, build config

Django
→ settings, apps, URLs, views, models, serializers, middleware,
  migrations, management commands, tests

Go
→ modules, packages, commands, interfaces, handlers, storage,
  tests, build tooling

Monorepo
→ workspace configuration, package boundaries, shared libraries,
  per-service manifests, cross-package imports, shared CI
```

Do not inspect irrelevant technology areas deeply.

For example:
- no Kubernetes files → Kubernetes-specific details are not part of the scan;
- no HTTP/API layer → API-specific areas may be `NOT_APPLICABLE`;
- no database → persistence areas may be `NOT_APPLICABLE`.

## Phase 4 — Deterministic Scan

Use deterministic analysis to collect facts quickly.

### Preferred fast path

Use existing tools first:

```text
git ls-files
rg
language/compiler tooling already installed
package-manager metadata
framework configuration
```

Collect facts such as:

- file counts
- file extensions
- largest source files
- manifests and lockfiles
- dependency declarations
- test files
- route definitions
- environment variable usage
- migration files
- CI jobs
- Dockerfiles
- lint/format configuration
- logging calls
- TODO/FIXME/HACK markers
- security configuration
- deployment files
- import relationships
- source/test naming patterns

### Adaptive scanner

If repository structure is too large or facts cannot be gathered efficiently, generate a temporary repository-specific scanner.

Preferred implementation:
- Python standard library where possible.
- Language-native AST/compiler APIs when already available.
- No network access.
- No package installation.
- No writes to source files.

Possible analyzers:

```text
Python       → ast
TypeScript   → TypeScript compiler API if available
JavaScript   → existing parser/tooling if available
Go           → go list / go/packages if available
Rust         → cargo metadata
Java         → Maven/Gradle metadata + static file analysis
.NET         → dotnet project metadata
```

The scanner should output structured facts, preferably JSON, for the LLM to interpret.

Example:

```json
{
  "languages": {},
  "frameworks": [],
  "manifests": [],
  "largest_files": [],
  "tests": {},
  "imports": {},
  "routes": [],
  "env_usage": [],
  "ci": {},
  "containers": {},
  "migrations": {},
  "security": {}
}
```

The scanner is an evidence collector, not the final decision-maker.

## Phase 5 — Targeted Evidence Search

After the deterministic pass, inspect only the files needed to resolve the 120 areas.

Do not read every source file linearly.

Prioritize:

1. explicit configuration
2. manifests
3. framework entry points
4. representative modules
5. tests
6. deployment configuration
7. documentation
8. repeated code patterns

For conventions, sample multiple files before labeling something `INFERRED`.

One example is not a convention.

## Phase 6 — Evaluate the 120 Areas

Every area must receive a status.

For each area determine:

```text
Status
Current rule/state
Evidence
Confidence, when needed
Conflict, when present
```

Do not turn missing areas into recommendations unless the user explicitly requests recommendations.

# Evidence Rules

## Strong evidence

Examples:

```text
eslint.config.js explicitly enables a rule
pyproject.toml configures Black
CODEOWNERS assigns a directory
GitHub Actions requires tests
Dockerfile sets USER app
Django middleware explicitly enables CSRF
README defines the branch workflow
```

These normally produce `DEFINED`.

## Repeated structural evidence

Example:

```text
14 feature directories all use:
feature/
  components/
  hooks/
  api/
  types/
```

This can produce `INFERRED` with `HIGH` confidence.

## Weak evidence

Example:

```text
one component happens to use camelCase
```

This is not enough to infer a repository rule.

Use `UNCERTAIN` or `NOT_DEFINED`.

## Conflicting evidence

Example:

```text
README says tests use pytest
CI runs unittest
new tests use pytest
```

Record the conflict.

Do not silently normalize it.

# Existing CONSTITUTION.md

If `CONSTITUTION.md` already exists, **refresh it instead of automatically performing another full scan**.

1. Read the existing constitution first.
2. Parse its scan metadata.
3. Determine what changed since the previous scan.
4. Invalidate only findings affected by those changes.
5. Re-evaluate affected areas and their immediate dependents.
6. Preserve unchanged sections byte-for-byte where practical.
7. Preserve explicit human rules unless the user asks to replace them.
8. Detect implementation drift from established rules instead of silently rewriting those rules.
9. Fall back to an expanded or full refresh when the previous state cannot be trusted.

Prefer stable numbered headings so later runs can patch areas in place.

---

# Smart Refresh Engine

## Goal

A normal development change should **not** trigger another 120-area full repository scan.

Use this lifecycle:

```text
FIRST RUN
Full discovery
→ Full 120-area scan
→ Generate CONSTITUTION.md
→ Save refresh metadata

LATER RUNS
Read CONSTITUTION.md
→ Detect repository changes
→ Map changes to affected areas
→ Invalidate affected evidence
→ Rescan only affected areas
→ Check immediate dependent areas
→ Detect drift
→ Patch changed sections
→ Refresh Agent Operating Summary if needed
→ Update scan metadata
```

Default to the cheapest refresh mode that can still produce trustworthy findings.

---

## Refresh Metadata

Store refresh state **inside `CONSTITUTION.md`** so this skill still creates only one persistent file.

Use a machine-readable HTML comment near the top:

```md
<!-- constitution-meta
schema_version: 1
scan_mode: full
scan_commit: a91cfe2d8f...
scan_timestamp: 2026-08-16T16:58:00Z
dirty_snapshot:
  backend/app/services/auth.py: sha256:...
untracked_snapshot:
  backend/tests/test_new_auth.py: sha256:...
-->
```

Rules:

- `scan_commit` is the Git `HEAD` observed by the previous scan.
- `dirty_snapshot` stores hashes only for tracked files that were modified at scan time.
- `untracked_snapshot` stores hashes only for relevant untracked files that were included in the scan.
- Never store secret values.
- Do not store hashes for ignored dependency/build directories.
- Do not create a separate metadata file.
- Metadata is implementation state, not an agent rule.
- Update metadata only after `CONSTITUTION.md` has been successfully patched.

Why dirty hashes matter:

A commit hash alone cannot describe a scan performed on an uncommitted working tree. The stored dirty/untracked hashes let a later refresh determine whether those exact contents changed, disappeared, or were committed unchanged.

## Change Detection

### Preferred Git path

When Git is available and the previous `scan_commit` still exists:

1. Read the previous `scan_commit`.
2. Compare it to current `HEAD`.
3. Collect added, modified, deleted, and renamed files.
4. Inspect current working-tree changes.
5. Compare files present in the previous `dirty_snapshot` and `untracked_snapshot` by content hash.
6. Build one normalized `changed_files` set.

Prefer commands such as:

```text
git diff --name-status <scan_commit>..HEAD
git status --porcelain
git ls-files
git rev-parse HEAD
git cat-file -e <scan_commit>^{commit}
```

Do not assume the working tree is clean.

### Important dirty-tree rule

If a file was dirty during the previous scan and is now committed with identical content:

- its stored hash matches the current file;
- do **not** treat it as a meaningful new change merely because Git history now contains it.

If the file contents differ from the stored hash, invalidate findings that depend on it.

### No Git / unusable history

Use an expanded or full refresh if:

- the repository is not under Git;
- the previous commit no longer exists;
- history was rewritten in a way that makes the previous baseline unreliable;
- metadata is missing/corrupt;
- file-level change detection cannot be trusted.

For small non-Git repositories, a deterministic file fingerprint pass may be used instead.

---

## Evidence-Driven Invalidation

The strongest refresh signal is the evidence already recorded in the constitution.

For each changed, deleted, or renamed file:

1. Find constitution areas whose `Evidence` references that path.
2. Mark those areas `INVALIDATED` internally.
3. Rescan them before keeping or changing their findings.

Example:

```md
### 63. Authentication approach

**Evidence**
- `backend/app/middleware/auth.py`
- `backend/app/core/firebase_admin.py`
```

If `backend/app/middleware/auth.py` changes, area 63 must be re-evaluated.

If an evidence file is deleted or renamed:

- do not keep the old evidence reference;
- search for its replacement;
- downgrade to `UNCERTAIN` or `NOT_DEFINED` if the finding can no longer be supported.

## Dependency Propagation

After finding directly affected areas, check **immediate dependents**.

Examples:

```text
dependency/runtime change
→ build/tooling
→ tests
→ CI

API contract change
→ request/response validation
→ frontend/client usage
→ tests

database schema change
→ migrations
→ persistence
→ API contracts
→ tests

authentication change
→ authorization
→ middleware/API behavior
→ security controls
→ tests

deployment config change
→ environment
→ health checks
→ CI/CD
→ rollback/release
```

Default propagation depth: **one dependency hop**.

Do not recursively propagate until every area becomes invalidated.

Escalate refresh mode instead if the dependency graph becomes broad or uncertain.

## Three Refresh Modes

### FAST REFRESH — default

Use when:

- the previous metadata is valid;
- repository structure is stable;
- a small/localized set of files changed;
- affected areas can be identified confidently.

Process:

```text
detect changed files
→ evidence invalidation
→ impact routing
→ one-hop dependency check
→ targeted rescan
→ patch affected sections only
```

### EXPANDED REFRESH

Use when:

- manifests/framework configuration changed;
- auth/security architecture changed;
- database schema/migration strategy changed;
- CI/CD or deployment structure changed;
- major directories were added/moved/removed;
- several related areas are invalidated;
- a change can alter the Agent Operating Summary;
- the static impact map is broad but still understandable.

Process:

```text
targeted rescan
+
rescan the affected constitution section(s)
+
rescan directly dependent section(s)
+
refresh project snapshot/summary as needed
```

### FULL REFRESH

Use when:

- `CONSTITUTION.md` has no usable metadata;
- constitution schema changed incompatibly;
- the previous Git commit cannot be resolved;
- Git history was rewritten and the old baseline is unreliable;
- the repository underwent a major framework/runtime migration;
- monorepo/workspace structure changed substantially;
- a very large portion of relevant source/config changed;
- too many areas become invalidated to trust selective refresh;
- the constitution appears corrupted/stale beyond safe patching;
- the user explicitly requests a full refresh.

Heuristic guidance, not rigid law:

```text
small/localized change
→ FAST

roughly 20–100 relevant files, or structural/config changes
→ EXPANDED

more than roughly 100 relevant files,
more than roughly 25% of relevant repository files,
or broad architectural uncertainty
→ FULL
```

Repository size matters. Prefer percentage/impact over absolute counts for very small or very large repositories.

## No-Change Fast Exit

If:

- current `HEAD` matches the previous baseline;
- dirty/untracked relevant files match the stored snapshots;
- no relevant new files exist;
- `CONSTITUTION.md` itself has not been manually changed in a way requiring reconciliation;

then:

1. do not rescan the 120 areas;
2. do not rewrite `CONSTITUTION.md`;
3. report that the constitution is current.

This should be the cheapest path.

---

## Patch-Only Update Rule

During FAST or EXPANDED refresh:

> **Patch findings; do not regenerate the whole document.**

If an area is unaffected:

- preserve its wording;
- preserve its evidence;
- preserve its status;
- avoid cosmetic rewriting.

Bad refresh:

```diff
- Firebase authentication is used.
+ Authentication is implemented with Firebase.
```

when authentication did not change.

Good refresh:

```diff
### 63. Authentication approach
- Firebase authentication...
+ Firebase authentication with email/password and passkeys...
```

only because authentication actually changed.

This keeps Git history meaningful and avoids constitution churn.

## Agent Operating Summary Refresh

Do not automatically rewrite the entire summary.

Regenerate or patch only summary fields whose source areas changed.

Examples:

```text

```

## Drift Detection

A refresh must distinguish:

```text
repository convention changed intentionally
```

from:

```text
implementation drifted away from an established rule
```

### Explicit human rule

If a human-authored rule says:

```text
Routers must call services; routers must not access the database directly.
```

and new code violates it:

- preserve the rule;
- do not rewrite the constitution to normalize the violation;
- add a drift warning.

Example:

```md
### 34. Layering/dependency direction
**Status:** DEFINED

- Routers → Services → Models/Core.
- Routers must not query the database directly.

**Drift**
- `backend/app/routers/payments.py` now performs a direct database query.

**Evidence**
- `AGENTS.md`
- `backend/app/routers/payments.py`
```

### Enforced configuration changed

If the finding was defined by actual configuration and that configuration intentionally changed:

- update the finding;
- update evidence;
- propagate to dependent areas.

Example:

```text
Node 20 → Node 22 in Dockerfile + CI
```

Area 19 should change rather than be marked as drift.

### Inferred convention changed

If an inferred pattern becomes inconsistent:

- resample nearby code;
- lower confidence or mark `UNCERTAIN`;
- only adopt a new convention when repeated evidence supports it.

One violating file should not automatically redefine an established inferred pattern.

---

## Human Edits to CONSTITUTION.md

Treat manual edits carefully.

When `CONSTITUTION.md` changed since the previous scan:

1. distinguish metadata/generated-section changes from apparent human edits;
2. preserve clear human-authored rules and notes;
3. do not overwrite them merely because the repository differs;
4. report drift where implementation violates them;
5. if authorship cannot be determined safely, preserve the text and mark the affected finding `UNCERTAIN`.

Generated observations are refreshable.

Human rules are authoritative unless the user explicitly asks to revise them.

---

## Refresh Integrity Checks

Before committing a refresh to the file, verify:

- every invalidated area was re-evaluated;
- evidence paths still exist or are intentionally recorded as deleted;
- renamed evidence paths were updated;
- immediate dependents were considered;
- unchanged areas were not cosmetically rewritten;
- the summary matches refreshed high-value areas;
- drift is distinguished from intentional configuration changes;
- secret values are absent;
- metadata describes the repository state that was actually scanned.

Only then write the updated metadata.

# CONSTITUTION.md Format

The output has two layers:

1. **Agent Operating Summary** — compact, immediately actionable repository context.
2. **Full Repository Constitution** — all 120 evidence-backed areas.

The summary must be generated from the completed 120-area scan, not independently guessed.

Use this structure.

```md
# Codebase Constitution

> Generated from repository evidence.
> Last scan: YYYY-MM-DD

<!-- constitution-meta
schema_version: 1
scan_mode: full
scan_commit: <git-commit-or-null>
scan_timestamp: <ISO-8601>
dirty_snapshot: {}
untracked_snapshot: {}
```

# Agent Operating Summary Rules

The summary exists to save future agents from re-discovering the repository before ordinary work.

It should usually fit in roughly **40–80 lines** and contain only high-value operational context.

Include:

- technology stack and major services
- architecture and dependency direction
- naming/import conventions that affect edits
- API and persistence contracts
- test/build/lint commands
- environment and deployment path
- security/auth model when relevant to implementation
- hard constraints and high-impact conflicts

Do not include:

- generic software explanations
- every dependency
- every folder
- low-value `NOT_APPLICABLE` findings
- long evidence lists
- speculative recommendations
- duplicated detail already available in the 120-area body

### Summary Selection Rule

A finding belongs in the Agent Operating Summary only if knowing it would likely change how an agent:

- chooses a file to edit
- structures new code
- imports or calls another module
- validates requests/responses
- accesses data
- writes or runs tests
- handles auth/security
- builds the project
- deploys/releases it
- avoids a known repository hazard

If it does not affect one of those decisions, keep it in the full constitution only.

### Conflict Priority

Surface the most consequential unresolved conflicts first, especially those involving:

1. working tree vs committed state
2. build/test/CI behavior
3. database/schema/migrations
4. runtime versions
5. authentication/authorization
6. secrets/security/privacy
7. deployment/environment configuration
8. stale documentation that could mislead an agent

# Compactness Rules

Do not make `CONSTITUTION.md` an encyclopedia.

For each area:

- 1 short status line
- 1–4 bullets describing the current rule/state
- 1–5 high-value evidence references
- confidence only when useful
- conflict note only when needed

Avoid explaining generic software concepts.

Bad:

```md
REST is an architectural style invented by...
```

Good:

```md
### 40. API style/protocols

**Evidence**
- `src/api/routes/`
```

# Repository Scanning Strategy

Use a funnel:

```text
Level 1 — Repository map
        ↓
Level 2 — Config/manifests/instructions
        ↓
Level 3 — Deterministic fact collection
        ↓
Level 4 — Representative source samples
        ↓
Level 5 — Targeted deep inspection only for unresolved areas
```

Do not start with a full semantic read of the repository.

This keeps the scan fast and reduces token use.

---

# Large Repository Strategy

For large repositories:

1. Discover workspaces/services first.
2. Scan shared/root configuration once.
3. Scan each major application/module separately.
4. Sample repeated structures rather than reading every file.
5. Use deterministic counts and searches for repository-wide patterns.
6. Deep-read only high-value files.
7. Merge findings into the single 120-area constitution.

If different applications use different conventions, document the differences.

Example:

```md
### 83. Linting rules/tooling
**Status:** DEFINED

- `apps/web`: ESLint
- `services/api`: Ruff
- `services/worker`: golangci-lint

**Evidence**
- `apps/web/eslint.config.js`
- `services/api/pyproject.toml`
- `services/worker/.golangci.yml`
```

# Safety & Integrity

Never:

- write to source files during discovery
- run destructive commands
- run migrations
- deploy
- modify databases
- rotate secrets
- install dependencies without permission
- execute unknown scripts merely to inspect them
- expose secret values in `CONSTITUTION.md`
- include `.env` secret contents
- copy credentials/tokens into scanner output

It is acceptable to record:

```md
Secrets are loaded from environment variables.
```

It is not acceptable to record:

```md
DATABASE_PASSWORD=actual-secret
```

---

# Secret Redaction

If secrets are discovered, record only:

- secret mechanism
- variable/key name when safe
- source file path
- whether the value appears hard-coded

Never record the secret value.

Example:

```md
### 68. Secrets scanning/storage
**Status:** UNCERTAIN
**Confidence:** HIGH

- A hard-coded credential-like value appears to exist in application code.
- Secret value intentionally omitted.

**Evidence**
- `src/integrations/provider.ts`
```

# Completion Gate

## Full scan

Do not finish a first/full scan until:

- all 120 areas have a status
- applicable identified areas have evidence
- explicit and inferred rules are distinguished
- the Agent Operating Summary was generated from the completed findings
- the Agent Operating Summary contains only implementation-relevant context
- high-impact unresolved conflicts are surfaced in the summary
- secret values are excluded
- contradictions are surfaced
- generated/dependency directories were not mistaken for source code
- refresh metadata reflects the repository state actually scanned
- the output exists as `CONSTITUTION.md`
- no persistent scanner artifacts remain
- no unrelated repository files were modified

## Incremental refresh

Do not finish a FAST/EXPANDED refresh until:

- change detection completed successfully
- all directly invalidated areas were re-evaluated
- immediate dependent areas were considered
- unaffected areas retained their previous valid findings
- deleted/renamed evidence was reconciled
- drift was surfaced instead of silently normalized
- summary-relevant changes were reflected in the Agent Operating Summary
- unchanged sections were not cosmetically regenerated
- refresh metadata was updated last
- secret values remain excluded
- no unrelated repository files were modified

A refresh does **not** need to re-read or rewrite all 120 areas when their previous findings remain valid.
